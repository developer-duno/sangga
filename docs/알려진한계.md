# 알려진 한계 (기준선)

> **이 문서의 목적**: 매 세션 같은 것을 다시 발견하고 다시 조사하는 낭비를 막는다.
> 여기 있는 것은 **"이미 아는 것"** 이다. 새 세션은 이 목록을 먼저 읽고, 여기 없는 것만 조사한다.
>
> 담는 것 = **사실이지만 지금 구조상 어쩔 수 없거나, 나중에 손봐야 하는 것.**
> 담지 않는 것 = 고칠 수 있는 결함(그건 `PROGRESS.md`의 "다음 단계"로 간다).
>
> 최초 작성 2026-08-08 (3차 적대검증 legacy-limits 관점, 23개 항목 전수 사실 확인).
> **새 한계를 발견하면 여기 추가하고, 해소되면 취소선 처리 후 해소 근거를 남긴다.**

## 5. 설계·검증 방법론의 한계

| 한계 | 근거 |
|---|---|
| **`v_floor_stack`이 전역 최신 분기로 점포를 고른다** | `snapshot_ym = (select max(snapshot_ym) from unit_business)` — 지역 필터가 없다. 여러 지역·분기가 쌓이면 최신 분기에 없는 지역이 **통째로 빈 층**으로 보인다. Phase 5 착수 전 필수 수정 |
| **`v_unit_current`를 스택뷰에 쓰면 전 호실을 공실로 오판** | `unit_id`가 전 행 NULL이라 63,717행 100%가 공실 판정. 뷰 주석에 ⛔ 명시 |
| **`unit_business (pnu, floor_no)` 인덱스가 없다** | `v_floor_stack`의 점포 lateral이 정확히 이 조합으로 필터. 강남 6.4만 행에선 무해, 전국이면 필요 |
| **`v_coverage_stats`는 화면을 열 때마다 전량을 센다** | 각주 숫자를 런타임 계산하려고 `count(*)`로 최신 분기 전체를 훑는다. 강남 6.4만 행에선 수십 ms라 무해하지만 **전국 수백만 행이면 화면 로드마다 부담**이 된다 — 그때는 집계 결과를 표에 적재하거나 materialized view로 바꾼다. 또한 `v_floor_stack`과 **같은 전역 최신 분기**를 쓰므로 지역별 분기로 바꿀 땐 **둘을 반드시 함께** 고쳐야 한다(따로 고치면 화면과 각주가 다른 분기를 말한다) |
| **`count(*) over ()`는 lim을 줄여도 비용이 안 준다** | 정확한 전체 건수를 위해 매칭 전부를 센다(실측 lim=1 254ms vs lim=100 277ms). "N개 이상"이라는 부정직한 표기를 피하기 위한 **의도된 대가** |
| **선별력 없는 검색어는 인덱스가 오히려 손해다** | `로`처럼 거의 모든 주소에 들어가는 한 글자는 트라이그램 인덱스가 무용하고, GIN 조회+heap 재확인 + UNION 두 가지 훑기·중복제거 비용만 더해진다. 라이브 실측(2026-08-08): 정밀 검색 152→**51~70ms**(2~3배 개선) / 광범위 `로` 272→**351ms**(30% 악화). **실사용 경로가 정밀 검색이라 절충은 맞지만 "무조건 빨라졌다"고 기억하지 말 것** |
| **옥탑(99)과 실제 99층을 구분할 수 없다** | 규격 자체의 한계. 강남 실측 최대 \|층\|=35라 현재 영향 0 |
| **L4 기본 규칙("반경 500m 동일층 실거래 5건 이상")이 1·2층에서만 절반쯤 선다** | 강남 12,274필지 전수 계산(2026-08-08, 좌표 100%·실거래 1,637건 기준). 5건 이상 확보되는 필지 비율: **1층 56.4% / 2층 48.7% / 3층 25.3% / 5층 4.3% / 지하1층 0%**. 층을 안 따지면 92.1%지만 그건 상가에서 의미가 없다(1층과 5층은 값이 배 단위로 다르다). 바탕도 얇다 — 실거래를 가진 필지 **369/12,274 = 3.0%**, (필지·층) 조합 822개 중 2건 이상은 **39%** | §6.1·§7이 "전 층에 시세를 낸다"를 전제하면 성립하지 않는다. **3층 이상은 L5(지역평균) 폴백이 사실상 기본값**이 되므로, 자동 확장 규칙의 기대 분포를 이 숫자로 다시 잡아야 한다 |
| **그럴듯한 일치율이 판별력 0일 수 있다** | 층 목록 대조 99.8%가 **난수 300회에도 100% 일치**했다. 근거를 세울 땐 **귀무가설(랜덤) 대조를 반드시 병행** |
| **`ORDER BY` 없는 `LIMIT`은 매번 다른 결과** | 검증관 스스로 이 함정을 밟아 213개를 227→218로 잘못 셌다. 페이지네이션엔 항상 `order` 명시 |
| **v_floor_stack은 anon이 전량 스크레이핑 가능** | PostgREST 1,000행/요청 × 94회면 93,696행 전부. 원본이 공개 데이터라 위법은 아니나 **가공물 전량 복제는 가능** |
| **프론트 번들 408KB(gzip 117KB)** | 대부분 `@supabase/supabase-js` 전체(auth·realtime·storage 포함). 앱은 `.from()`·`.rpc()`만 쓴다 |

## 0. 쉬운 설명 (여기까지만 읽으셔도 됩니다)

**무엇을 했나.** 화면에 넣을지 검토 중인 "시세 어림값" 기능이 실제로 얼마나 맞는지 시험을 봤습니다. 컴퓨터에게 **2025년 말까지의 거래만** 보여주고, **2026년에 실제로 팔린 구분 상가 2,534건의 가격을 맞혀 보라**고 한 뒤, 진짜 계약 가격과 비교해 채점했습니다. 답안지를 미리 보여주지 않는 시험입니다. 채점한 거래는 **화면이 값을 낼 수 있는 거래만**입니다(대장에 그 층이 있고, 주거·오피스텔 층이 아닌 거래 — 그 해 거래 3,525건 중 2,534건 · §1).

**어떻게 어림하나.** 곁의 거래를 아래 순서로 찾아, 찾은 가격들의 중간값을 씁니다(위가 안 되면 아래로 내려가는 사다리입니다). 어느 칸이든 **그 층의 대장 용도와 같은 종류(상가·업무·숙박·기타) 거래끼리만** 셉니다(결정 0040) — 업무 층에는 업무 거래만, 상가 층에는 상가 거래만:

1. 같은 건물 같은 층에서 팔린 적이 있으면 → 그 가격
2. 없으면, 걸어서 1~2분 거리(100m) 안의 같은 층 가격들
3. 그래도 없으면, 500m 안의 같은 층 가격들
4. 그래도 없으면, 같은 동네(법정동)의 비슷한 층 평균

**비교 상대.** "그 구(區)에서 같은 층대·같은 용도 묶음 거래의 평균" — 상가 거래에는 화면의 『층대별 거래 단가』(상가 거래 기준)와 같은 값입니다. 새 방식이 이것보다 낫지 않으면 만들 이유가 없습니다.

**결과 — 세 줄.**

- 새 방식의 어림값은 **절반의 거래에서 실제 가격의 ±25% 안**에 들어왔습니다. 구 평균 방식은 ±35%였습니다. → **새 방식이 더 정확합니다.**
- 실제 10억에 팔린 상가로 바꿔 말하면 — 새 방식은 보통 **7.5억~12.5억 사이**로 어림했고, 구 평균 방식은 6.5억~13.5억 사이였습니다.
- "±20% 안에 맞히면 합격"으로 치면, 새 방식은 **10건 중 약 4건 합격**, 구 평균 방식은 약 3건이었습니다.

**하지만 조심할 것 3가지.**

1. **잘 맞는 방법일수록 쓸 수 있는 곳이 적습니다.** 제일 정확한 "같은 건물" 방법(오차 ±13%)은 3건 중 1건꼴로만 가능했고, 절반이 넘는 46%는 맨 아래 "동네 평균"까지 내려갔습니다.
2. **1층이 제일 안 맞습니다**(오차 ±44%). 같은 1층이라도 코너 자리냐 골목 안쪽이냐로 값이 크게 갈리는데, 그 차이는 공공데이터에 없습니다. 오히려 3층 이상이 잘 맞습니다(±18%).
3. **어떤 구에서는 새 방식이 구 평균만 못합니다**(아래 4-1 표에서 구별로 확인). 그래서 "잘 맞는 지역·층만 골라 보여주는" 안전장치가 꼭 같이 가야 합니다.

**한 줄 요약.** 새 방식이 더 낫다는 건 숫자로 확인됐지만, "어디서나 믿을 만하다"는 아닙니다. 상가는 아파트와 달리 바로 옆 가게끼리도 값이 크게 다르기 때문에, 어림값은 "이 가격이다"가 아니라 **"이 언저리다"**로만 쓸 수 있습니다. 이 아래 §1부터는 그 근거 숫자들입니다.

## 1. 방법

- **대상**: `transaction` 중 `tx_type='집합'` + PNU·층·단가가 모두 있고 지분 거래가 아닌 거래 **13,418건**(서울 11,509 · 대전 1,909).
- **열린 지역(서울·대전 30개 구)만** 채점한다 — 화면이 여는 구(`list_open_sigungu()`)의 거래만 남겼다(결정 0013 §7). 열린 지역 밖 제외: 시도 12 1,840건.
- **시간 분할**: 학습 `contract_ym <= 202512` **9,893건** / 검증 `contract_ym >= 202601` **3,525건** / 범위 밖 **0건**. 합 13,418 = 전체 13,418.
  랜덤 분할을 쓰지 않는다 — 미래로 과거를 맞히면 성적이 부풀려진다(CLAUDE.md 검증 규칙).
- **용도 묶음(결정 0040)**: 상가(1·2종 근린생활·판매) / 업무 / 숙박 / 기타(교육연구·그 밖). 후보 거래의 묶음 = 그 거래의 건물 주용도 이름(`transaction.main_use` · 화면의 `price_use_group_nm`) · 검증 거래의 묶음 = **그 층의 대장 용도**(`price_floor_use_group` — 정본 본문을 psql 한 세션의 `pg_temp` 에 만들어 불렀다 · 운영 쓰기 0). 모든 단계와 대조군이 같은 묶음 후보만 본다.
- **채점 집합(결정 0040 D10)**: 검증 거래 3,525건 중 층 묶음이 넷 가운데 하나인 **2,534건**만 채점했다 — 화면이 값을 낼 수 있는 거래만. 묶음별: 상가 1,602건 · 업무 501건 · 숙박 216건 · 기타 215건. 뺀 갈래: 대장에 그 층이 없음 841건 · 주거 층(floor_resid) 61건 · 오피스텔 층(floor_officetel) 89건 · 대장 용도 코드 빈칸(no_use) 0건.
- **추정값**: 각 단계 후보 거래 단가의 **중앙값**. 후보는 **학습 거래만**이다.
- **오차**: APE = |추정 − 실제| / 실제. 주지표는 **MdAPE(오차 중앙값)**, 보조로 MAPE(평균)와 **±20% 적중률**.

### 단계 정의

| 코드 | 후보 조건 | 최소 표본 |
|---|---|---|
| L2 | 같은 필지(PNU) + 같은 층 + 같은 묶음 | 1 |
| L4 | 반경 100m 이내 + 같은 층 + 같은 묶음 | 3 |
| L5 | 반경 500m 이내 + 같은 층 + 같은 묶음 | 5 |
| L6 | 같은 법정동(PNU 앞 10자리) + 같은 층대 + 같은 묶음 | 1 |
| BASE | 같은 시군구 + 같은 층대 + 같은 묶음 | 1 (사다리 밖 · 비교 상대 · 결정 0040 D10) |
| (참고) 옛 BASE | 같은 시군구 + 같은 층대 (용도 불문 — v2 의 대조군) | 1 (판정에 안 씀 · §4-3) |

- 코드 번호는 `docs/상세계획.md` **§6.2 사다리의 단계 번호**를 그대로 쓴다(2=동일 건물 동일 층 / 4=반경 100m / 5=반경 500m / 6=행정동→법정동). `docs/상세계획.md` 앞부분의 공간 레벨 표(L1 층·L2 건물·L3 가로…)와는 다른 축이니 번호만 보고 겹쳐 읽지 말 것.
- **운영 모드(사다리 걷기)** = L2→L4→L5→L6 순서로 걸어 **처음 성립하는 단계**를 채택. 아무 것도 성립하지 않으면 `no_estimate`.
- **BASE 는 사다리에 넣지 않는다.** "구 평균만 말했을 때"와 견주기 위한 대조군이다 (`docs/알려진한계.md` §5 — 그럴듯한 수치가 판별력 0 일 수 있어 귀무가설 대조를 병행한다).
- 거리는 haversine(미터). 반경 단계는 **양쪽 좌표가 다 있어야** 성립하고, 검증 거래에 좌표가 없으면 `coords_missing` 으로 따로 센다(표본 부족과 구분).
- 층대: 음수=지하 / 1층 / 2층 / 3층+ / 옥탑(99).

## 2. 데이터 한계 (성적을 읽기 전에)

- **지번이 공개되는 2024-01 이후 집합 거래만 채점됐다.** 일반(통건물) 거래는 지번이 마스킹돼 PNU 조립이 0%라 아예 대상에 못 든다 — 이 성적은 **집합 상가에 한정된 성적**이다.
- **채점 대상의 층대 분포**: 지하 0건 · 1층 3,556건 · 2층 2,509건 · 3층+ 7,353건 · 옥탑 0건 · 층미상 0건. 지하가 0건인 것은 2017년부터 실거래 원본에 지하층 표기가 오지 않기 때문이다(우리 파싱 문제가 아니다 — `docs/알려진한계.md`). 즉 이 성적은 **지하층에 대해서는 아무 말도 하지 않는다**.
- **좌표 결측**: 검증 거래 3,525건 중 필지 좌표가 없어 반경 단계를 못 돌린 거래 **0건**(0.0%). 이 거래들은 버리지 않고 `coords_missing` 으로 세어 커버리지에 반영했다.
- **단가 분포(원/㎡, 전체 13,418건)** — 극단값을 **버리지 않고 그대로 채점했다**. 잘라내면 성적이 좋아 보이지만 실제 화면은 그 거래도 만나기 때문이다.

## Phase 3 선행 — 실거래 수집·적재 ✅ (2026-08-08 새벽, 계획보다 앞당김)

**왜 지금 했나**: 실거래는 **건축물대장과 별개 API라 한도가 따로**다(`MOLIT_KEY`). 건축물대장 수집이 도는 동안 병렬로 돌려도 서로의 예산을 먹지 않는다. 게다가 전국 확장은 6~20일짜리 작업이라 일찍 시작할수록 일정이 당겨진다.

| 산출물 | 내용 |
|---|---|
| `collect_transactions.py` | API → raw JSONL. 이어받기(`collect_progress`, collector=`rtms_commercial`)·일 예산·안전 종료·raw 원자성. 테스트 52개 |
| `load_transactions.py` | raw → `transaction`. PNU 조립·만원→원 변환·층 정규화·해제 거래 제외·`tx_id` 멱등 생성. 테스트 60개 |
| 파일럿 실행 | 강남 20년 **240콜 / 2.3분 / 23,599건** (§5.3 예상 10분보다 빠름) |
| 라이브 적재 | `transaction` **22,662행** (해제 937건 제외) |

**§5.6의 빈 지표 2개를 채웠다** (지번 공개 구간 2024-01~ 기준):

| 지표 | 목표 | 실측 |
|---|---|---|
| 실거래 → PNU 조립 (집합) | 90%+ | **99.9%** ✅ |
| 실거래 → PNU 조립 (통건물) | "낮을 것" | **0%** (구조적 불가) |
| 조립된 PNU → parcel 매칭 | — | **93.2%** |

**★ 로드맵에 영향을 주는 발견 — 지번은 2024-01부터 공개된다**: 2023-12까지는 지번이 100% 마스킹(`'6**'`)이라 PNU 조립이 원천 불가하다. 2024-01에 68.6%로 갑자기 바뀐다(제도 변경). → **§5.3 3단계 백필(54,000콜·6~20일)은 PNU를 붙일 수 없는 데이터를 받는 작업**이므로 우선순위를 낮춘다. 다행히 계획이 "시세 추정에는 최근 24개월만 쓴다"고 정해 둬서 중요한 구간은 전부 공개 범위 안이다. 상세는 `docs/상세계획.md` §5.3·§5.6.

> ⚠️ **조립률을 전체 기간으로 재지 말 것** — 전체 23,599건 기준이면 7.8%로 찍히는데, 그건 품질이 아니라 제도 시점을 재는 것이다. 건축물대장에서 "수집 커버리지와 조인 성공률을 섞지 말라"고 했던 것과 같은 함정.

### Phase 2 사전 조사 결과 (2026-08-07 야간 라이브 실측) ★

**결론: 호실 축으로 스택뷰를 만들면 강남 건물의 82%가 빈 화면이 된다. 층별개요 테이블 신설이 선행 작업이다.**

| 실측 항목 | 값 |
|---|---|
| `unit_business.unit_id` 채움률 | **0%** (64,239행 전부 NULL) |
| `unit_business.ho` 채움률 | **0%** (§3.3 "호정보 전수 결측"이 사실로 확인) |
| `unit_business.floor_no` 채움률 | 67.1% |
| **호실(unit)이 있는 건물** | **1,083 / 5,903 = 18.35%** |
| 건물은 있으나 호실 없는 PNU | 4,575개 |
| 점포 행 중 호실 있는 PNU 소속 | 9,224 / 64,239 = **14.36%** |
| 점포 행 중 (PNU+층) 매칭 | 5,187 / 64,239 = **8.07%** |

- **왜 18%뿐인가**: 전유공용면적(호실)은 **집합건물에만 존재**한다. 단독 근생 등은 층·호로 쪼갠 대장이 애초에 없다.
- ⚠️ **기존 뷰 `v_unit_current`를 그대로 쓰면 안 된다**: `x.unit_id = u.unit_id`로 점포를 붙이는데 unit_id가 전부 NULL이라 **63,717행 100%가 `is_vacant=true`(공실)로 판정**된다. 라이브 조회로 확인함
- ✅ **§5.6의 95.85%는 틀리지 않았다 — 다른 것을 잰다**: §5.6 ②(b)는 "점포가 속한 **필지**에 building이 붙었나"만 보고 층·호 단위 조인은 측정하지 않는다(`load_building_ledger.py:1050` 주석이 "감사 지적 #7의 별도 과제"라고 이미 명시). 위 14.36%/8.07%가 그 별도 과제의 답이다
- **처방**: `getBrFlrOulnInfo`(층별개요)는 호실 구분과 무관하게 **모든 건물**에 층별 면적·용도가 있다. 스택뷰를 "호실 쌓기"가 아니라 **"층 쌓기"** 로 만들면 나머지 82%에서도 그려진다.
- 데이터 등급: 층 단위 집계로 가면 "몇 호가 공실"은 말할 수 없고 **"이 층에 빈자리가 있는 듯"** 수준의 **D등급(간접 추론)** 이 된다 → 화면에서 시각적 구분 필수

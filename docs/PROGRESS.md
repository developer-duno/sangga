**Phase 0에서 추가로 밝혀진 것 (Phase 1 설계에 영향)**

- 상권정보 배포본은 **호정보가 전수(100%) 결측** → 호실 축은 건축물대장 전유부로 채워야 한다(설계대로).
- 층정보 결측(54.75%)은 무작위가 아니라 **비수도권·숙박업 구조 쏠림**(서울 37.33% ~ 경북 71.91%, 군 단위 90%대, 숙박업 87.9%) — 건축물대장 보정 우선순위에 반영 필요.
- 파일럿 강남구는 결측률·업종 구성이 전국과 달라 **파일럿 성적이 전국 대표성을 보장하지 않는다** → Phase 3 백테스트에 비수도권 대조 지역 포함 권고.
- 2017Q3 분기 파일은 컬럼·업종 체계가 다른 이례 파일 — 시계열 정제 시 전용 처리 필요.
- Supabase 8GB 한도 대비 전국 41분기 확장 시 ~64GB 전망 — 전국 확장 전 요금·설계 재검토 필요.

## 다음 단계

1. **[P0]** 건축물대장 이어받기 수집 2일차 — 일 한도(엔드포인트별 1만) 리셋 후, 잔여 6,618 PNU + 실패 40건(`--retry-failed`). Phase 1 완결의 유일한 blocker
   - ⚠️ **`--dry-run`의 잔여 예산 표시를 그대로 믿지 말 것 (2026-08-07 야간 실측)**: dry-run이 "전유공용면적 292건 잔여"로 판정했으나 실제 호출에서 포털은 **이미 쿼터 초과**로 거절했다(처리 0건·안전 종료, 오염 없음). 우리 계수기(`api_quota_log`)는 **우리가 보낸 횟수**만 세는데 포털 집계는 그보다 앞선다 — dry-run 잔여는 **상한이지 보장이 아니다.** 잔여가 수백 건 수준이면 사실상 소진으로 간주하고 자정 리셋을 기다리는 편이 낫다
2. **[P1]** 수집 완료 후 재적재 → §5.6 조인률 **확정**(현재 95.71%/95.85%는 수집 45.76% 시점 잠정치) → 90%+ 유지되면 Phase 1 통과 판정
3. **[P2]** 절단 PNU 4개 방침 결정 — 전부 대형 **아파트**(대청아파트·대청타워·래미안블레스티지·미도맨션)라 상가 분석 우선순위 낮음. **`numOfRows` 상한은 공식 문서에 없다(2026-08-07 실측)** — 공공데이터포털 상세·건축HUB 소개·건축물대장 레퍼런스 3곳 모두 미명시이고 명세는 활용가이드 zip 안에만 있다. 문서를 뒤지는 대신 **API 1콜 실측**으로 확정할 것: `numOfRows=1000`으로 요청해 응답 행 수가 1000이면 허용, 100으로 깎이면 상한 100
4. **[P3]** Phase 2(층별 스택뷰 + 지도) 착수 — **착수 전 아래 조사 결과 필독.** "호실 수" 집계는 `(bld_id, ho)` DISTINCT 기준으로 설계할 것(복층이 층별 2행이므로)

### Phase 2 사전 조사 결과 (2026-08-07 야간 라이브 실측) ★

**결론: 호실 축으로 스택뷰를 만들면 강남 건물의 82%가 빈 화면이 된다. 층별개요 테이블 신설이 선행 작업이다.**

| 실측 항목 | 값 |
|---|---|
| `unit_business.unit_id` 채움률 | **0%** (64,239행 전부 NULL) |
| `unit_business.ho` 채움률 | **0%** (§3.3 "호정보 전수 결측"이 사실로 확인) |
| `unit_business.floor_no` 채움률 | 67.1% |
| **호실(unit)이 있는 건물** | **1,083 / 5,903 = 18.35%** |
| 건물은 있으나 호실 없는 PNU | 4,575개 |
| 점포 행 중 호실 있는 PNU 소속 | 9,224 / 64,239 = **14.36%** |
| 점포 행 중 (PNU+층) 매칭 | 5,187 / 64,239 = **8.07%** |

- **왜 18%뿐인가**: 전유공용면적(호실)은 **집합건물에만 존재**한다. 단독 근생 등은 층·호로 쪼갠 대장이 애초에 없다.
- ⚠️ **기존 뷰 `v_unit_current`를 그대로 쓰면 안 된다**: `x.unit_id = u.unit_id`로 점포를 붙이는데 unit_id가 전부 NULL이라 **63,717행 100%가 `is_vacant=true`(공실)로 판정**된다. 라이브 조회로 확인함
- ✅ **§5.6의 95.85%는 틀리지 않았다 — 다른 것을 잰다**: §5.6 ②(b)는 "점포가 속한 **필지**에 building이 붙었나"만 보고 층·호 단위 조인은 측정하지 않는다(`load_building_ledger.py:1050` 주석이 "감사 지적 #7의 별도 과제"라고 이미 명시). 위 14.36%/8.07%가 그 별도 과제의 답이다
- **처방**: `getBrFlrOulnInfo`(층별개요)는 호실 구분과 무관하게 **모든 건물**에 층별 면적·용도가 있다. 스택뷰를 "호실 쌓기"가 아니라 **"층 쌓기"** 로 만들면 나머지 82%에서도 그려진다. **원본은 이미 확보**돼 있고(`data/raw/bldrgst/202608/flr_ouln.jsonl` 58MB) **담을 DB 테이블만 없다**(`schema.sql`에 표제부·호실만 존재. `unit.floor_use`는 호실 행에 붙는 값이라 대체 불가) → **Phase 2 착수 = 층별개요 테이블 신설 + 적재기 확장이 선행**
- 데이터 등급: 층 단위 집계로 가면 "몇 호가 공실"은 말할 수 없고 **"이 층에 빈자리가 있는 듯"** 수준의 **D등급(간접 추론)** 이 된다 → 화면에서 시각적 구분 필수

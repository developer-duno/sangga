# 결정 0005 — 전국 확장 실행 순서와 선행 조건

> 작성일 2026-08-10 · 갱신 2026-08-10(2차) · 상태: 🔸 **순서 확정 / [A] 결정 3건 + [C] 노선 1건 대기**
> 🆕 2차 갱신: [C] 단축 레버 4개를 **전부 확인 완료**했다(어제는 1개만 확인). 핵심 = **일괄 파일이 실재한다**.
> 사장님이 전국 확장을 결정(2026-08-10 자정)한 뒤 세운 실행 계획.
> ⚠️ **이 문서가 존재하는 이유**: 적대검증(2026-08-10)이 "실행 순서가 레포 어디에도 없고
> 세션 임시 폴더에만 있다"는 맹점을 잡았다. 임시 폴더는 세션이 끝나면 사라진다.

## 실행 순서 (바꾸지 말 것)

```
[A] parcel 전국 시드      상권정보 CSV → parcel 110만 + unit_business 272만
     ↓  (순서 엄수 — [B]는 [A] 없이는 채울 대상이 0이다)
[B] 토지특성 채움         브이월드 일괄 CSV 17파일 → parcel의 5+1 컬럼
     ↓
[C] 건축HUB 전국          건물·층별개요·전유공용면적  ⛔ 최대 병목 (아래 참조)
     ↓
[D] 실거래 전국 · district 경계 · 나머지
```

**왜 이 순서인가**: `parcel`이 모든 것의 분모다. [B]·[C]는 "parcel에 있는 PNU만" 다루도록
설계돼 있어(분모 오염 방지 불변식), [A] 전에 돌리면 **아무것도 안 채워지고 조용히 성공**한다.
실측: [B]를 강남만 있는 상태로 돌리면 3,589만 행이 "parcel 미보유"로 세어지고 12,261건만 갱신됐다.

## [A] parcel 전국 시드 — 착수 전 결정 3건

### ⛔ 결정 1: 기준 분기를 Q1(202603)로 할 것인가 Q2(20260630)로 할 것인가 👤

- 현재 `data/raw/sangkwon/`에는 **Q1(202603) CSV 17개가 압축 해제된 상태**(1.4GB)
- Q2는 `data/raw/sangkwon_zips/…20260630.zip`에 **zip 그대로** 있고 풀려 있지 않다
- `load_sangkwon_snapshot.py`의 `DEFAULT_DATA_DIR`가 `data/raw/sangkwon`이므로
  **아무 생각 없이 실행하면 Q1이 적재된다**
- Q2로 갈 것이면 별도 폴더에 풀고 `--dir`를 명시할 것. **기본값 실행 금지.**

### ⛔ 결정 2: 아래 코드 결함 3건을 [A] 전에 고칠 것인가 👤

적대검증(2026-08-10)이 확인한 것들. 전부 **전국 규모에서만 터진다**:

| # | 결함 | 왜 위험한가 | 위치 |
|---|---|---|---|
| 1 | **upsert 재시도 0회** | 전국 시드는 배치 **3,826회**(parcel 1,100 + ub 2,726). 한 번만 네트워크가 튀어도 **2시간이 통째로 날아간다**(멱등이라 데이터는 안 깨지지만 시간은 회수 불가). 처방 = `collect_building_ledger.py`의 기존 재시도 3회+지수 백오프 패턴 재사용 | `load_sangkwon_snapshot.py` upsert_batch |
| 2 | **`fetch_existing_parcels`가 limit/offset 페이지네이션** | 110만 행을 1,000씩 1,100번 넘기는 동안 다른 곳에서 INSERT가 일어나면 **행이 밀려 누락**된다. 처방 = keyset(`pnu=gt.<마지막>`) 또는 최소한 조회 후 `rest_count` 대조 게이트 | `load_vworld_land.py:167-207` |
| 3 | **[B]가 매칭 0건이어도 exit 0** | [A] 전에 실수로 [B]를 돌리면 **조용히 성공**한다. 형제 스크립트에는 있는 "적재할 행 없으면 실패" 가드가 없다 | `load_vworld_bulk.py` main |

### ⛔ 결정 3: [A]가 깨뜨리는 화면 성능 2건을 함께 처리할 것인가 👤

용량·요금은 문제없다(약 2.7GB, 마이크로 10GB 내 — 승급 불필요). 문제는 **화면 속도**다.
레포가 이미 "전국이면 손봐야 한다"고 예고해 둔 항목이 정확히 [A] 시점에 발동한다:

1. `v_coverage_stats`가 `unit_business` 전체를 스캔한다 → 272만 행이 되면 각주 숫자 조회가 느려진다.
   처방 = materialized view 또는 집계 표 전환, 최소한 [A] 직후 응답시간 실측 게이트.
2. `unit_business (pnu, floor_no, snapshot_ym)` 인덱스가 없다 → 층 스택 조회가 느려진다.

### [A] 실행 시 반드시 할 것

- ✅ **적재 후 `ANALYZE`** — PostgreSQL 공식이 대량 적재 후 강력 권장하는데 우리 적재기에 없다.
  안 하면 통계가 낡아 쿼리 플래너가 잘못된 계획을 골라 화면이 느려진다.
- 메모리: 시도 파일 1개당 **peak 약 1.4GB**(실측 — 1행당 1,609바이트. 코드 주석의 614B는 3.3배 과소).
  이 PC에서 치명적이진 않으나 "413MB라 안전"이라는 옛 판단 근거는 무효다.

### 단축 레버 — ✅ 4개 전부 확인 완료 (2026-08-10 2차 세션)

#### ④ 일괄 파일 — ✅ **존재한다. 이게 최대 레버이고, 나머지 3개를 무의미하게 만든다**

건축물대장을 API로 한 건씩 긁지 않고 **전국 파일을 통째로 받는 창구가 실재한다.**

| 항목 | 확인된 사실 | 출처 |
|---|---|---|
| 창구 | 건축HUB **대용량 데이터 제공 서비스** | [hub.go.kr 대용량 목록](https://www.hub.go.kr/portal/opn/lps/idx-lgcpt-pvsn-srvc-list.do) |
| 대상 | 건축물대장 **누적분 / 월변동분** | 위 동일 |
| 세부 파일 | 총괄표제부·**표제부**·**층별개요**·부속지번·**전유공용면적**·오수정화시설·공동주택가격·전유부·지역지구구역 (우리가 쓰는 3종 전부 포함) | [건축물대장 안내](https://www.hub.go.kr/portal/opn/tyb/idx-bdrg-epcm.do) |
| 갱신 | 매월 — **전월까지 갱신분을 익월 20일 제공** | hub.go.kr 대용량 목록 |
| 이용 조건 | **건축HUB 회원이면 누구나** (로그인 필요) | hub.go.kr 대용량 목록 |
| 규모 검산 | 표제부 **7,865,698행** / 전유공용면적 **109,467,774행** (전국) | 공공데이터포털 [표제부 15044720](https://www.data.go.kr/data/15044720/fileData.do) · [전유공용면적 15044714](https://www.data.go.kr/data/15044714/fileData.do) |

- **PNU 조립 가능**: 파일 필드에 `시군구코드·법정동코드·대지구분코드·번·지`가 그대로 들어 있다
  (포털 데이터 설명 실측). 우리 PNU 19자리 = 이 5개의 결합이므로 **브이월드 일괄 CSV와 똑같은
  패턴**으로 적재할 수 있다 — 이미 검증된 `load_vworld_bulk.py` 방식을 재사용하면 된다.
- ⛔ **아직 확인 못 한 것 (로그인 벽)**: 파일 **용량·형식·시도 분할 여부·실제 다운로드 절차**.
  `open.eais.go.kr`은 이 PC에서 **연결 거부**(ECONNREFUSED)라 자동 확인이 막혔고,
  hub.go.kr 목록도 로그인 후에만 파일 목록이 렌더링된다. 👤 **사장님이 로그인해 1회 확인 필요.**

#### ① 전유공용면적을 집합건물에만 호출 — ✅ **판별 정확도 100% 확정**

어제 "미확인"으로 남긴 전제(표제부 응답만으로 집합/일반을 가릴 수 있나)를 **강남 원본 전수로 검증했다.**
표제부 응답에 `regstrGbCd`/**`regstrGbCdNm`**(일반·집합) 필드가 실제로 들어 있다.

| 표제부에 '집합' 포함 | 전유공용 있음 | 전유공용 없음 |
|---|---|---|
| **집합** | 1,646 | 1 |
| **일반** | ⛔ **0 (놓침 0건)** | 10,126 |

- 표제부가 없는데 전유공용만 있는 PNU도 **0건** — 표제부 선행 전략에 사각지대가 없다.
- 호출 대상이 **13.99%**로 줄고 전유공용 콜이 **46.4% 절감**된다. ⇒ **215일 → 116일**.
- 구현 지점: `collect_building_ledger.py`의 `for endpoint in ENDPOINTS` 루프가 조건 분기 없이
  3종을 무조건 부른다. 호출 순서가 이미 표제부 → 층별개요 → 전유공용이라 **표제부 응답을 보고
  분기하면 된다**(순서 변경 불필요). `estimate_calls`의 배수도 같이 고칠 것.
- ⚠️ 옛 근거였던 "18.35%"는 **1일차 5,903행 시점의 건물 단위** 수치다. 호출 결정을 지배하는 건
  **PNU 단위 13.99%**(3일차 완주 원본). 둘은 같은 현상의 다른 분모이니 섞어 쓰지 말 것.

#### ② API 한도 증설 — ✅ **자동승인. 리드타임 없음 (어제 전제가 틀렸다)**

[국토교통부_건축HUB_건축물대장정보 서비스](https://www.data.go.kr/data/15134735/openapi.do) 공식 페이지 실측:

- 심의구분 = **개발단계 자동승인 / 운영단계 자동승인**
- 개발계정 신청가능 트래픽 = **일 10,000건** (우리 2026-08-07 라이브 실측과 일치)
- 운영계정 = 활용사례 등록 시 증설 신청 가능. 포털 일반 안내상 **일 최대 100,000건(10배)**
- 이용허락범위 **제한 없음**

⇒ 어제 이 문서가 "심사 기간이 리드타임이라 지금 당장 신청해야 한다"고 적은 것은 **과한 전제였다.**
자동승인이므로 [C] 착수 직전에 신청해도 늦지 않다. 다만 **운영계정 전환에는 활용사례 등록이
선행**되므로 그 준비(서비스 URL·스크린샷)는 미리 해 둘 수 있다.

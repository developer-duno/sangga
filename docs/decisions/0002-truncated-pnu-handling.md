# 결정 0002 — 건축물대장이 잘린 19개 PNU(대형 아파트), 화면에 뭐라고 보여줄까

> 작성일 2026-08-09 · 상태: ⬜ 결정 대기 (사장님 승인 필요)
> 근거 문서: `docs/알려진한계.md` §2 절단 PNU 행 · `docs/PROGRESS.md` "다음 단계" P2 항목 · `docs/상세계획.md` §5.3 numOfRows 실측 (줄번호 인용은 병행 편집으로 밀리므로 섹션 참조로 통일)

## 무엇을 정해야 하나

건축물대장 API는 한 번에 최대 100건씩, 최대 100페이지(1만 건)까지만 준다. 강남구 안에서 이
상한에 걸린 필지(PNU)가 **19개** 있다(★ 2일차 시점 13개 → 3일차 완주 후 2026-08-09 적재기 재계수로 **19개**. 적재기는 실행 시점에 raw를 다시 세므로 개수는 코드가 자동 추적한다) — 2일차에 확인된 13개는 전부 세대수 많은 대형 아파트다(대청아파트·은마아파트·
개포자이 프레지던스 등). 3일차 재계수로 추가된 6개는 건축물대장에 건물명이 비어 있어 개별 미확인이다. 이 필지들은 "건물 층별 상세"(면적·용도 프로필)가 일부만 저장된다.
이걸 화면에서 어떻게 다룰지 지금 정한다.

---

## 지금 상황 — 이미 확인된 사실 (재조사 안 함)

- API 페이지당 최대 100건(`numOfRows`, 실측 확정) × 최대 100페이지(`MAX_PAGES`) = 1만 건 상한.
  예: 어떤 PNU는 전유공용면적 응답이 실제로 `totalCount=30,935`건인데 1만 건까지만 받아진다(주1).
- 이 상한에 걸린 PNU는 **19개**. 2일차 시점에 확인된 13개는 전부 대형 아파트 단지다: 대청아파트·대청타워·래미안블레스티지·
  미도맨션·은마아파트·개포자이 프레지던스·디에이치아너힐즈·개포 래미안 포레스트·래미안 강남힐즈·
  강남한양수자인·현대아파트(압구정)·미성아파트·일원동우성7차아파트(주2). 3일차 추가 6개의 PNU 목록은 `load_building_ledger.py --dry-run`이 실행 시점마다 다시 세어 출력한다.
- 적재기(`load_building_ledger.py`)는 이 19개를 **이미 자동으로 감지해 안전하게 제외한다** —
  절단된 raw로 옛(멀쩡한) DB 행을 지우지 않는다(`find_truncated_pnu` + `_delete_stale_rows`의
  3중 잠금 중 하나)(주3). 코드 결함이 아니라 이미 방어돼 있는 상태다. 이 문서는 "버그를
  고치는" 문서가 아니라 "화면에 뭐라고 보여줄지"만 정하는 정책 문서다.
- 이 절단이 가리는 것은 **건축물대장에서 나오는 층별 상세(면적·용도)뿐**이다. 상가 점포
  목록(`unit_business`)은 완전히 별개 파이프라인(상권정보 분기 CSV, `load_sangkwon_snapshot.py`)
  에서 나오고 PNU만으로 붙는다 — 건축물대장 적재기와 코드가 전혀 겹치지 않는다. 그래서 이
  19개 필지에서도 점포 목록 자체는 정상 표시된다(직접 확인: `unit_business`를 채우는 스크립트는
  `load_sangkwon_snapshot.py` 하나뿐, 2026-08-09 grep 재확인)(주4).

## 선택지 A — 지금처럼 자동 제외 유지 + 화면에 "일부 상세 없음" 배지만 추가 (권고안)

**무엇을 하는 방식인가**: 재수집을 하지 않는다(API 예산을 안 쓴다). 대신 이 19개 PNU를
조회하면 스택뷰에 "건물 층별 상세 일부 누락(대형 단지, 수집 상한)"이라는 D등급 경고를
붙인다(절대 규칙 3의 근거 레벨 표기 원칙, `docs/상세계획.md` §5.6 폴백 경고와 같은 방식의
재사용).

| 항목 | 내용 |
|---|---|
| 장점 | API 호출 예산을 안 씀. 강남구 1개 구를 완주하는 데도 3일이 걸리는 지금 상황에서 우선순위를 지킴 |
| 잃는 것 | 이 19개 건물의 층별 상세(면적·용도)는 계속 일부만 보임 |
| 절대 규칙 위반 소지 | 없음 — 없는 데이터를 만들지 않고 사실대로 경고만 붙임 |
| 되돌리기 | 쉬움 — 나중에 예산이 남으면 B안으로 전환 가능 |

---

## 선택지 B — 이 19개만 `MAX_PAGES`를 올려 재수집

**무엇을 하는 방식인가**: 코드 변경은 사실상 없다(`MAX_PAGES`는 이미 상한값이라 올리면
자동으로 더 받아온다). 이 19개 PNU만 한정해서 페이지 상한을 300~400 정도로 올려 재수집한다.

| 항목 | 내용 |
|---|---|
| 장점 | 층별 상세가 완전해짐 |
| 잃는 것 | API 호출 비용 — 예: `totalCount=30,935`인 PNU 하나만도 지금(100페이지)의 3배 이상(약 310페이지) 필요. 19개 전부 하면 그만큼 예산 소모 |
| 절대 규칙 위반 소지 | 없음 |
| 되돌리기 | 언제든 가능 — 예산이 넉넉해지면 즉시 착수할 수 있는 안 |

> **검토했으나 이번엔 제외한 방법**: "이 19개를 통째로 상가 분석 대상에서 제외"하는 안도
> 생각해볼 수 있지만, 상가 점포 목록(`unit_business`) 자체는 이미 정상 표시되므로 이 필지의
> 점포 검색·조회를 막을 이유가 없다. 점포는 그대로 보여주고 "건물 상세"만 배지로 알리는
> 쪽이 더 정직하다.

## 권고 — A

1. 확인된 13개는 전부 **주거용 대형 아파트**고, 추가 6개도 같은 절단 패턴(전유부 1만 행 초과 = 세대수 많은 대형 집합건물)이다. 이 프로젝트의 핵심 표적(상가 공간분석)이 아니다.
2. 상가 점포 존재 자체(`unit_business`)는 이미 안 가려진다 — 절단이 감추는 건 건물 층별
   상세뿐이다.
3. 강남구 1개 구 완주에도 API 예산 3일이 드는 지금, 우선순위가 낮은 19개 아파트에 예산을
   쓰는 건 손해다.
4. 적재기는 이미 안전하게 방어돼 있다(멀쩡한 행을 지우지 않음) — 급하게 고쳐야 할 버그가
   아니라 "화면에 뭐라고 보여줄지"만 남은 정책 질문이다.

### 되돌리기 조건

Phase 2 사용자 검증("아는 건물 8개 눈 검증") 중 이 19개 중 하나가 실제로 자주 조회되거나,
사장님이 "이 아파트 단지 상가가 중요하다"고 특정하면 B안으로 전환한다.

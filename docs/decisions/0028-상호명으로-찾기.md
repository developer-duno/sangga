## 무엇이 문제인가

검색창은 **건물 이름과 주소**만 안다. 그런데 결정 0014 가 적었듯 **창업자는 건물 이름을 모른다** —
"스타벅스 있는 건물", "○○떡볶이 자리"로 찾는다. 점포 자료는 **339만 행·상호 100% 채움**인데
그 자료로 들어오는 문이 하나도 없다(2026-08-19 자산 감사: "점포 338만이 사용자에게 안 닿음").
상호명이 화면에 나오는 곳은 층을 펼쳤을 때의 점포 목록뿐이라, **이름을 아는 사람만** 그 화면에
도달한다 — 순서가 거꾸로다.

## 결정 1 — 별도 함수 `search_stores(q, lim, sigungu, p_offset)`, 기존 검색 함수는 손대지 않는다

- 서명은 형제 순서 `search_stores(q text, lim int default 50, sigungu text default null, p_offset int default 0)`.
  ⛔ `sigungu` 가 비면 **0건**(0007).
- **형제의 전처리를 글자 그대로 상속**: `security definer` + `set search_path = public` · 입력 `% _ \` 이스케이프 ·
  빈 검색어 0건 · `lim` 은 `greatest(1, least(coalesce(lim,50),200))` · `search_key(q)` · `count(*) over ()`.
- 최신 분기만 — ⚠️ **전역** 최신 분기(지역별 분기가 어긋나면 그 지역 가게가 통째로 안 나오는 결함을 `v_floor_stack` 과
  똑같이 물려받는다 — 로드맵 "이번에 안 하는 것" 표의 알려진 결함). ⛔ 폐업 추정 금지 — 지난 분기 가게는 **안 나온다**.
  결과 구역에 "**2026년 6월 기준 점포 자료**" 도장(서버 값 — 숫자 리터럴 0).
- 닫힌 채로 태어난다: public revoke · `api.search_stores` 쌍둥이만 anon grant · `ANON_CALLABLE_ALLOWLIST` **20 → 21**
  (`--check` 총계 24 → 25 · `tests/test_post_load.py:462` 튜플 동반 수정).
- **함수가 내보내는 칸**: `pnu` · 대표 동 칸(0025 와 같음) · `matched_names text[]`(최대 3) · `match_store_cnt` ·
  `bld_cnt_in_pnu` · `total_parcel_cnt` · `total_store_cnt` · `too_broad boolean` · `snapshot_ym`. ⛔ `biz_no`·좌표·
  업종 코드는 안 나간다.
- ⛔ 게이트에 걸리면 **0건이 아니라 `too_broad=true` + `total_store_cnt` 한 줄**(지금의 `search_scope` 는 상호를 안 세고,
  그걸 고치면 "기존 함수 불변"이 깨진다).
- 정규화는 건물과 **같은 자** `search_key()`. 실익은 대소문자(영문 6.9만)뿐이지만 같은 검색어에 건물과 상호가 다른
  답을 내지 않게 한 자로 간다.

## 결정 2 — 결과 한 줄은 **땅(필지)** · 50줄 + 더 보기 · **층은 v1 줄에 안 적는다**

- 한 줄 = `pnu` · 대표 동(연면적 최대) 이름·주소·지번 · **일치한 상호 최대 3개 + "외 N곳"** · `bld_cnt_in_pnu`
  ("같은 땅에 N동" — 펼치기 `list_parcel_buildings` 재사용) · `match_store_cnt`.
- **층은 적지 않는다** — 층 결측이 셋 중 하나이고(있을 때만 적으면 없는 줄이 1층으로 읽힌다), 층을 가져오려면
  찾은 땅마다 점포 표를 되짚어야 하는데 그 2단계가 **찬 캐시 3.2초**(실측 ⑤)다. 층은 누른 뒤 층별 화면의
  점포 목록이 보여준다(이미 있는 화면).
- 정렬: 일치 가게 수 → 정확 일치(`search_key` 같음) → 주소 → **`pnu`**(tie-break).
- **50줄 + 더 보기**(`p_offset`) · 서버 상한 200 · 경쟁 가드 — 0025 결정 3 을 **글자 그대로**(`DistrictBuildings.tsx`
  페이지 부품 재사용). 건물 결과의 "이 중 N개만" 관습과 다르므로 두 구역이 각자 제 관습대로.
- 누르면 **층별 화면으로**. ⛔ 문구는 "**이 땅에** 있는 가게"(0025 의 `store_cnt` 함정).

## 결정 3 — 흔한 단어는 **필지별 "가게 이름" 형제 요약표**로 푼다 (✅ 사장님 결재 ① · 2026-09-10 구현 중 모양 전환)

⚠️ **전환 기록(2026-09-10 새벽)**: 3판은 `mv_search_parcel` **자체에** 두 칸을 더하려 했다. 그런데 구현 1차에서 그 표에
**기대어 사는 물건이 넷**(`mv_open_sigungu` → `mv_coverage_stats` → `v_coverage_stats` → `api.v_coverage_stats`)이라 칸을
더하려면 다섯을 한 트랜잭션에서 지우고 다시 세워야 했고, 그 과정은 각주 뷰의 정본 규칙 "⛔ drop 하고 다시 만들지 말 것"
(anon 권한 유실 사고)을 어기며 정본↔라이브 드리프트(2026-09-01 감사에서 함수 8개)를 라이브에 실어 나를 위험이 있었다.
그래서 **기존 표와 사슬은 한 글자도 안 건드리고 형제 표 하나를 새로 만든다.** 결과 단위(땅)·속도·크기는 같고 결재 취지
("277만 행짜리 새 표는 안 만든다")도 그대로다 — 이 표는 필지(19만 이하) 단위다. 사장님께는 안전 모드 정지 보고(2026-09-10
00:20)에서 사슬 사실을 알렸고 "끝까지 이어간다" 승인을 받았다.

새 물질화뷰 **`mv_parcel_store_names`** — 건물이 있는 필지(`mv_search_parcel` 과 같은 포함 규칙, 단 그 표를 **참조하지
않는다** — 참조하면 사슬에 우리가 하나 더 매달린다) 중 **최신 분기 점포가 1곳 이상인 땅**만:

| 칸 | 내용 | 쓰임 |
|---|---|---|
| `pnu`(유일) · `sigungu_code` | 땅 · 구(앞 5자리) | 1단계에서 구로 먼저 좁힌다(`idx_mpsn_sigungu`) |
| `store_names text[]` | 그 땅 최신 분기 점포의 상호 **원문**, 점포마다 한 항목(중복 포함 — distinct 로 접으면 일치 가게 수를 못 센다) | 화면에 적을 일치 상호 3개 + 개수 — `unnest` 로 **한 줄 안에서** 센다(2단계 되짚기 없음 → 3.2초 소멸) |
| `store_names_key text` | distinct `search_key(이름)` 을 `\|` 로 이은 것 | 1단계 땅 찾기 — trgm 색인 `idx_mpsn_names` |
| `store_cnt` · `store_snapshot_ym` | 점포 수 · 사용한 최신 분기(전 행 동일) | 요약 · 화면 도장 |

- 1단계: `sigungu_code = 구` 뒤 `store_names_key like`. 2글자 검색어는 색인을 못 타도 구 안 1.2만 행 순차 훑기라 **10ms**,
  4글자는 색인 **0.6ms**(강남 시제품 실측 — 같은 크기·같은 모양).
- 크기(강남 시제품 → 30개 구 환산): 표 ~30MB · 색인 ~150MB. **지우는 `idx_ub_name` 186MB 로 상쇄**(마이그레이션 **맨 끝**에서
  drop — 잠금이 커밋까지 유지되는 함정은 2026-08-22c 주석대로). DB 총 5.3GB 에서 순증 0 이하.
- 마이그레이션은 `begin/commit` 안에서(0027 가드) — **drop 은 맨 끝 `idx_ub_name` 한 줄뿐**이라 기존 검색·각주는 **잠기지
  않는다**. 그래도 새 표 굽기(277만 점포를 땅별로 접음)와 gin 색인에 수 분이 걸릴 수 있어 새벽에 적용.
- 갱신: `post_load.py` `REFRESH_MVS` 에 **한 줄 추가**(`mv_search_parcel` 다음 · 의존 없음 · `refresh … concurrently` 전제로
  유일 색인 `idx_mpsn_pnu`). ⚠️ 갱신 시간이 는다 — 구현 PR 에서 전후 시간을 재어 기록.
- **범위 게이트**: 1단계 일치 **땅 수** > `search_scope_limit()`(6,000) 이면 `too_broad` 한 행. 구 안 최다가 '학원' 강남 898땅이라
  **구로 좁힌 검색은 닿지 않는다**(안전망으로만).
- 기각: ~~`mv_search_parcel` 에 칸 추가(3판 안)~~(위 전환 기록) · ~~새 요약표 `mv_search_store` 277만 행~~(표 단위가 점포) ·

## 결정 4 — 화면: 같은 검색창, 결과는 **두 구역, 늘 함께** (✅ 사장님 결재 ②)

- 검색하면 건물 질의와 상호 질의를 **나란히** 보내고, "건물 N개" 아래 "**이 이름의 가게가 있는 땅 M곳**" 구역을
  하나 더 그린다. 사용자가 고를 것 없음 · 검색 한 번에 서버 두 번.
- **경쟁 상태·부분 실패**: 지금의 `latestRun` 하나를 **두 질의가 공유**(늦게 온 옛 답은 둘 다 버림) · 에러 상태는
  **구역별로 따로** · 상호 질의만 실패하면 건물 결과는 서고 상호 구역에 "가게 이름 결과를 불러오지 못했습니다"
  (0025 규칙 — 사람이 누른 결과는 조용히 사라지면 안 된다) · **함수 부재**(PGRST202 — 배포 순서)만 조용히 생략.
- 한 글자 차단·구 미선택 차단 그대로. **"너무 넓은 검색어" 창은 껍데기만 재사용**, 문구·숫자는 상호용
  ("이 이름의 가게가 N곳입니다 — 더 좁혀 주세요").
- placeholder: `건물명 · 도로명주소 · 지번 · 가게 이름 (예: …, 스타벅스)`. ⚠️ **placeholder 를 지키는 시험이 0개**라
  vitest 에 문구 가드를 **새로** 만든다. `aria-label` 은 **바꾸지 않는다**(바꾸면 vitest 9곳 + E2E 2곳).
- **모바일**: 좁은 폭에서는 **세로로 쌓는다**(`styles.css:2505-2510` 선례 — "넓은 화면만 보면 이 깨짐을 못 잡는다").
- **인쇄**: 새 구역은 반드시 `<section class="search">` **의 자손**(`.search` 가 `@media print` 에서 통째로 빠진다 —
  형제로 빼면 종이에 남는다).

## 결정 5 — 사람 이름이 든 상호는 **그대로 둔다** (사장님 위임 2026-09-09 — "목적·사용자 편의·미래가치·실증·데이터 관리")

1. **성질이 다르다** — 건물 쪽 가림은 대장에 딸려 온 **소유자 이름**('… 단독주택 (김남연)' 93건)을 지운 것이다.
   상호는 사업자가 **스스로 간판에 내건 공개 이름**이고 공공데이터 원문이다.
2. **이미 보인다** — 층 목록에 상호가 그대로 나온다(0015 결재). 검색만 가리면 "보이는 것 = 검색되는 것" 원칙이
   깨지고, '홍길동 공인중개사'를 찾는 사용자(그게 상호다)가 못 찾는다.
3. **기계 가림은 자료를 망친다** — 느슨한 정규식으로도 16.4만(5.9%)이 잡히는데 대부분 '행복부동산'류 오탐(실측 ③).
   상호에서 사람 이름을 확실히 골라낼 방법이 없다.
4. **되돌릴 길은 열어 둔다** — 의견함에 "내 이름을 지워 달라"가 오면 그때 `biz_no` 단위 예외 표(표시·검색 둘 다)를
   별건 결재로. 원본은 안 건드린다(건물 가림과 같은 원칙).

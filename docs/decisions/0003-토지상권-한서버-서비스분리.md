# 결정 0003 — 토지·상권 데이터는 한 서버로, 서비스는 따로

> 작성일 2026-08-09 · 상태: ✅ **승인 (사장님 결정 2026-08-09)** — 토지(필지) 데이터와
> 상권(상가) 데이터는 **한 서버(현 Supabase 프로젝트)에 함께** 담고, 사용자에게 보이는
> **서비스(화면·상품)는 따로** 만든다. 단 "어디까지 합치나"의 선을 아래에 함께 확정한다.
> 배경 대화: 전국 확장 소요 검토(전국 필지 실측 110만 개) 중 사장님 제안 → 검토 → 승인.

## 무엇을 정했나 (세 줄)

1. **원천·분석 데이터는 한 서버.** 필지(토지특성·공시지가·용도지역)·건물·호실·시세 통계는
   지금처럼 한 DB에 담는다. 토지 전용 서비스를 나중에 내더라도 **새 서버를 파지 않는다.**
2. **서비스는 따로.** 화면(프론트)은 상품마다 별도로 만든다. 단 **회원·결제·즐겨찾기 같은
   서비스 고유 상태가 생기는 순간, 그것은 공유 서버에 넣지 않고 그 서비스 소유로 분리**한다.
3. **mibunyang(아파트 미분양) 격리는 그대로 유지**(확정 설계 7 불변). 어떤 도메인을 이
   서버에 합칠지의 기준선 = **"같은 필지(PNU) 마스터를 쓰는가"** 하나다.

## 왜 합치는 게 맞나 (근거)

- **두 서비스의 심장이 같은 데이터다.** 토지 서비스의 본체(도로접면·공시지가·용도지역)가
  곧 상가 시세 추정의 최대 보정 변수다(주1). 확정 설계 1의 섹터 축에 이미 '토지'가
  들어 있고, 확정 설계 2의 3층 구조(필지→건물→호실)의 1층이 곧 토지 레이어다 —
  **데이터 차원에선 이미 합쳐진 설계**이며, 이 결정은 그것을 서비스 차원까지 연장한 것이다.
- **나누면 세 가지를 잃는다**: ① 전국 고유 필지 **1,099,599개**(주2)를 양쪽에 복제 저장
  ② 수집·적재·백업 파이프라인 2벌 유지 ③ **DB 경계를 넘는 PNU 조인 불가** — 이게 최대 손해다.
- **비용은 합치는 쪽이 싸다.** 현재 마이크로 플랜($10/월)이고, 전국 41분기 ~64GB 용량
  문제(주3)는 합치든 나누든 똑같이 터진다. 합치면 요금제 결정을 한 번만 하면 되고,
  나누면 두 번 하는 데다 필지 데이터가 중복 과금된다.
- **운영자가 한 명이다.** 이 프로젝트는 RLS 누락·search_path 함정·PostGIS 시스템 표
  노출(주4) 같은 DB 보안 함정을 이미 여러 번 실측으로 밟고 문서에 박아뒀다. 서버가
  2개면 같은 관리를 두 곳에서 반복해야 한다.

## 감수하기로 한 것 (눈 뜨고 받아들인 리스크)

| 리스크 | 크기 | 완화책 |
|---|---|---|
| 장애 반경 — DB 하나 죽으면 두 서비스 다 죽음 | 감수 | 조회형 서비스 + 사전계산 정적 JSON(성능 원칙)이 완충 |
| 자원 경합 — 한쪽 무거운 쿼리가 다른 쪽을 느리게 함 | 중간 | "무거운 건 사전계산" 원칙으로 구조적 방어. 필요 시 read replica 검토 |
| 마이그레이션 실수가 양쪽에 전파 | 중간 | 상품화 시점에 서비스별 Postgres 스키마 분리로 경계 긋기 |
| 회원 체계 결합 — Supabase는 프로젝트 하나 = 회원 체계 하나 = 공개 키 하나 | 지금 0, 방치 시 큼 | **결정 2번 항목으로 사전 차단** — 서비스 고유 상태는 공유 서버에 안 넣는다 |

## 기각한 대안 — 서버 완전 분리 (서비스마다 DB 하나씩)

- 장점: 장애 격리 완전, 회원 체계 충돌 원천 차단.
- **기각 사유**: 위 "나누면 잃는 세 가지"가 그대로 비용이 된다. 1인 운영 + 같은 필지
  기반 + 로그인 없는 공개 조회형이라는 현 조건에서는 격리의 이득이 복제·이중 운영의
  비용을 못 넘는다. 회원 체계 충돌은 완전 분리 없이도 결정 2번(상태 분리 원칙)으로 막힌다.

## 이 결정이 발동되는 시점 (가드레일 — 지금 바꿀 코드는 0건)

1. **전국 확장의 요금·저장 설계 시점**(주3의 "전국 확장 전 반드시 재결정" 항목) —
   그 결정은 이 문서의 전제(한 서버) 위에서 한다. 서버 분리안을 다시 꺼내지 않는다.
2. **토지 서비스 상품화 착수 시점** — 첫 작업은 서비스별 Postgres 스키마 분리다.
   회원·결제 테이블을 공유 서버에 만들지 않는다(결정 2번). 스키마 경계·이름 규칙의
   구체 기준은 이 문서가 정하지 않는다 — 그 시점의 새 결정 문서(0004+)로 정한다.
3. **새 도메인 편입 판단** — "PNU 필지 마스터를 쓰는가"로 판정한다. 쓰면 이 서버,
   안 쓰면 별도(예: mibunyang은 계속 별도).
4. 이 문서는 가드레일이다. 위 1~3 시점이 오기 전에는 이 결정으로 인해 해야 할
   구현 작업이 없다.

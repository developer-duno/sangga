# 결정 0001 — 지하2층 이하·옥탑, 근거 없는 층의 시세를 어떻게 보여줄까

> 작성일 2026-08-09 · 상태: ⬜ 결정 대기 (사장님 승인 필요)
> 근거 문서: `docs/상세계획.md` §6.1 두 개 박스 · `docs/알려진한계.md` §1 (줄번호 인용은 병행 편집으로 밀려나 섹션 참조로 통일 — 2026-08-09)

## 무엇을 정해야 하나

앞으로 만들 "추정 시세" 기능(Phase 3)은 건물의 각 층마다 매매·임대 시세를 계산해서 보여줄
계획입니다. 그런데 실제로 데이터를 세어 보니, 우리 건물 층 데이터(`building_floor`
135,619개, 3일차 완주 후 2026-08-09 재계산) 중 **4곳 중 1곳꼴(26.2%)은 시세를 계산할 재료 자체가 없습니다** — 지하1층·
지하2층 이하·옥탑입니다. 이런 층을 만났을 때 화면에 무엇을 보여줄지, 코드를 짜기
**전에** 지금 정해야 합니다. 나중에 정하면 코드를 다시 짜야 해서 손해가 큽니다.

---

## 지금 상황 — 재료가 없는 층이 왜, 얼마나 있나 (이미 확인된 사실, 재조사 안 함)

임대료 추정 공식은 이렇게 생겼습니다(주1):

```
추정 임대료 = (추정 매매가 × 지역 수익률 ÷ 12) × 층별효용비율
```

여기서 "층별효용비율(= 층마다 임대료가 얼마나 차이 나는지 보여주는 정부 공식 계수)"과
"추정 매매가(= 실제 거래된 가격 중앙값으로 추정)" 둘 다 층별로 확인했더니, 아래 층들은
이 공식 자체가 성립하지 않았습니다.

| 층 | 전체 중 비중(주2) | 매매: 실제 거래 기록이 있나 | 임대: 정부 공식 계수표에 이 층이 있나 |
|---|---|---|---|
| 지하1층 | 13.6% (18,401개) | ⛔ **2017년부터 전국에서 0건**(주3) | ✅ 있음 — 단, 곱할 매매가가 없어서 못 씀 |
| 지하2층 이하 | 7.8% (10,556개) | ⛔ 위와 같은 이유로 없음 | ⛔ **공식 계수표에 이 구간 자체가 없음**(주1) |
| 옥탑 | 4.8% (6,524개) | ❔ 이번 조사에서 따로 세어보지 않음(옥탑은 계단실·물탱크실이 많아 상가 거래 자체가 드물 것으로 짐작만 함 — 확인된 사실 아님) | ⛔ 공식 계수표에 이 구간 자체가 없음(주1) |
| **합계** | **26.2%** | | |

쉽게 말하면: **"이 층은 얼마다"라고 말할 근거 재료가 처음부터 없는 층이 전체의 4곳 중
1곳꼴**입니다. 이 문서는 이 층들에게 화면이 뭐라고 말할지를 정합니다.

### 왜 "이웃 층 값을 빌려 쓰면 되지 않나"가 쉬운 답이 아닌가

상가는 층마다 가격이 몇 배씩 차이 나는 게 정상입니다. 실제로 반경 500m 안의 같은 층
실거래를 다 세어 보니 **1층은 56.4%가 시세를 낼 수 있는데 5층은 4.3%뿐**이고,
**지하1층은 0%**였습니다(주4). "1층과 5층은 값이 배 단위로 다르다"는 게 이 프로젝트가
이미 세워둔 원칙입니다(주5). 그래서 옆 층 값을 그냥 가져다 쓰면 실제 값과 크게 어긋날
위험이 있습니다.

또 하나, 이 계수는 "지역"이 아니라 "상권"마다도 다릅니다. 같은 강남 안에서도 상권에
따라 지하1층 계수가 **1.8배**(테헤란로 22.7 vs 강남 상위 40.9, 2026년 2분기 실측) 차이가
납니다(주6). 그만큼 "대충 비슷한 값을 넣는" 접근이 위험하다는 뜻입니다.

## 지금 화면은 무엇을 하고 있나 (코드로 직접 확인)

이 결정이 나기 전인 **지금도 지하·옥탑 층은 화면에 이미 그려지고 있습니다** —
`src/components/FloorStack.tsx`가 건물의 모든 층을 층수 순서대로 가져와 필터링 없이
전부 그리기 때문입니다(주7). 다만 지금은 **어느 층에도 시세(추정 매매가·임대료) 자체가
없습니다** — Phase 3가 아직 시작되지 않았기 때문입니다. 코드에 이렇게 직접 적혀 있습니다:

> "지금 채울 수 있는 칸은 층·용도·면적·점포 4개뿐이다. 추정 시세는 Phase 3 … 산출물이라
> 여기서는 그리지 않는다(빈칸을 그럴듯하게 채우면 없는 근거를 있는 것처럼 보이게 만든다)."
> — `FloorStack.tsx` 11~13줄

그러니까 **지금 당장 화면이 잘못 보여주고 있는 건 없습니다.** 이 문서가 정하는 것은
"Phase 3에서 시세 칸이 새로 생길 때, 지하·옥탑 칸에 무엇을 넣을 것인가"입니다.

한 가지 세부사항: 지하층(층 번호가 음수)에는 이미 다른 색(회색조) 스타일이 적용돼
시각적으로 구분되지만(`floor--under` 클래스, `styles.css` 236~257줄), 옥탑(층 번호 99)에는
이 스타일이 적용되지 않습니다 — 조건이 "층 번호가 0보다 작은 경우"만 보기 때문입니다
(`FloorStack.tsx` 139줄). 사소한 차이지만, 이번 결정으로 옥탑도 별도 표시가 필요해지면
같이 손볼 부분입니다.

## 선택지 A — 숫자를 안 보여주고 "근거 없음"이라고 정직하게 말한다 (권고안)

**무엇을 하는 방식인가**: 지하1층·지하2층 이하·옥탑은 추정 시세 숫자를 계산하지
않습니다. 대신 "왜 계산할 수 없는지"를 설명하고, 같은 건물 다른 층의 실제 거래 기록이
있으면 그것만 층수를 밝혀서 그대로 나열합니다(새 숫자를 만드는 게 아니라 이미 있는
사실을 보여주는 것뿐이라 안전합니다).

**화면 문구 예시**
```
지하2층 · 42평

📊 이 층은 추정 시세를 계산하지 않습니다
근거: 정부 임대료 공식표에 지하2층 이하 구간이 없고,
     2017년부터 이 지역 지하층 매매 실거래 기록도 없습니다.

참고할 수 있는 것: 이 건물 1층 실거래 3건 (지하2층과 다른 층이니 참고만 하세요)
```

| 항목 | 내용 |
|---|---|
| 장점 | 없는 숫자를 만들지 않음(절대 규칙 2·3 위반 소지 없음). 구현이 가장 단순 |
| 잃는 것 | 지하 매물을 찾는 사용자가 숫자를 하나도 못 봐 아쉬울 수 있음(26.2%의 층이 "빈 화면") |
| 기존 코드와의 일치 | `FloorStack.tsx`에 이미 같은 패턴이 있음 — 각주 통계를 못 가져오면 숫자를 빼고 "적지 않은 수"라는 말로만 대체함(89~96줄). 새 개념이 아니라 검증된 방식의 재사용 |
| 되돌리기 | **가장 쉬움.** 나중에 데이터가 생기면 계산을 추가하기만 하면 됨(좋은 소식). 반대로 "보여줬다가 근거가 약했다"고 정정하면 신뢰가 깎임 |

## 선택지 B — 이웃 층 계수를 빌려와 쓰되 "근거 약함" 배지를 크게 붙인다

**무엇을 하는 방식인가**: 지하2층 이하는 지하1층의 임대 계수를, 옥탑은 가장 가까운
실측 계수를 그대로 가져다 씁니다. 화면에는 "간접 추론" 경고 배지를 붙입니다.

| 항목 | 내용 |
|---|---|
| 장점 | 완전히 빈 화면보다는 "감이라도" 잡을 수 있음 |
| 잃는 것 | 지하는 아래로 갈수록 값이 낮아지는 게 보통인데, 지하1층 값을 그대로 쓰면 지하2층 가치를 실제보다 높게 보여줄 위험. `docs/상세계획.md`가 이미 "없는 계수를 이웃 층에서 임의로 만들어 쓰면 절대 규칙 3이 요구하는 근거가 사라진다"고 경고해 둔 바로 그 방식(주1) |
| 절대 규칙 위반 소지 | **있음.** 배지를 붙여도 "만들어낸 숫자"라는 사실은 그대로. 지금 이 결정 자체가 "이런 유추 로직을 만들지 말지"를 묻는 질문인데, 이 방식은 그 유추 로직을 새로 만드는 셈 |
| 되돌리기 | 어려움. 사용자가 이미 그 숫자로 판단했을 수 있어, 나중에 정정하면 신뢰가 크게 깎임 |

## 선택지 C — 그 층 대신 "건물 전체 평균"을 보여준다

**무엇을 하는 방식인가**: 지하2층·옥탑 단독 숫자 대신, 그 건물 다른 층들의 평균("건물
평균가")을 참고용으로 보여줍니다.

| 항목 | 내용 |
|---|---|
| 장점 | 완전한 공백보다는 "이 건물이 대략 어느 가격대인가" 정보는 남음 |
| 잃는 것 | 이 프로젝트의 핵심 전제와 부딪힘 — 1층과 5층은 값이 배 단위로 다른 게 정상인데(주5), 지하층에 지상층을 섞은 "건물 평균"을 보여주면 사용자가 그걸 지하2층 시세로 착각하기 쉬움 |
| 절대 규칙 위반 소지 | 문구를 아주 조심해서 설계하면 피할 수 있지만, 세 선택지 중 **오해를 부를 위험이 가장 큼** |
| 되돌리기 | 가능하지만, "층별 차등"이라는 이 프로젝트 근본 설계와 계속 부딪혀 두고두고 설명이 필요함 |

> **검토했으나 이번엔 제외한 방법**: "지하와 옥탑을 서로 다른 규칙으로 처리"하는 안도
> 검토했지만, 지하 쪽은 "언젠가 사람이 직접 임대 실사례를 모은다"는 새 데이터 수집
> 계획이 필요해 절대 규칙 2("요청 없는 기능·확장 금지")에 걸립니다. 지금 요청받지
> 않은 새 작업을 이 결정에 끼워 넣지 않기로 하고 제외했습니다.

## 권고 — A

1. 이 프로젝트는 이미 "표본이 부족하면 그 사실을 그대로 드러내는 것이 정직한 답"이라는
   원칙을 §6.2·§6.3에 세워 두었습니다(주4). 이번 결정은 그 원칙을 "표본이 아예 0인
   경우"로 한 단계 더 밀어붙이는 것뿐입니다.
2. `FloorStack.tsx`에 이미 "근거를 못 가져오면 숫자를 빼고 경고만 남긴다"는 코드가
   실제로 있습니다(87~96줄). 완전히 새로운 개념이 아니라 검증된 방식의 재사용입니다.
3. 절대 규칙 2("불필요한 유연성 금지")·3("근거 레벨+표본 수 병기") 양쪽에 가장 안전합니다.
4. **되돌리기가 제일 쉽습니다.** "안 보여주다가 나중에 보여주기 시작"은 사용자에게
   좋은 소식이지만, 반대로 "보여줬다가 근거가 약했다"고 정정하는 건 신뢰를 깎습니다.

단, 완전한 침묵은 아닙니다. "이 층의 추정 숫자"는 안 만들되, "이 건물의 다른 층
실거래 목록"은 층수를 명확히 표시하며 그대로 보여줍니다 — 새 숫자를 만드는 게 아니라
이미 있는 사실을 그대로 나열하는 것이라 절대 규칙에 걸리지 않습니다.

화면 문구는 기존 "표본 부족"(사다리를 다 돌았는데도 못 채운 경우, 주4)과 **구분**해야
합니다. 이번 경우는 "사다리를 돌 재료 자체가 없는" 더 근본적인 경우이므로 "표본 부족"이
아니라 "근거 데이터 없음" 같은 별도 문구를 씁니다 — "조금만 더 모으면 나오는 건가?"라는
잘못된 기대를 주지 않기 위해서입니다.

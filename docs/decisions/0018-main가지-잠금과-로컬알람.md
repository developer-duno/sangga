## 무엇이 문제였나

배포가 라이브로 나간 뒤에도 **main 가지가 완전히 열려 있었다.** 실측(2026-08-25):

| 확인한 것 | 결과 |
|---|---|
| 저장소 규칙(ruleset) | **0개** |
| 옛 방식 가지 보호(branch protection) | **없음**(404 Branch not protected) |
| 로컬 훅 | **0개**(`.git/hooks/` 에 견본 파일만, 활성 훅 없음) |

즉 `git push origin main` 한 번이면 **검사 없이 라이브가 바뀌는** 상태였다. 이 저장소는
`main` 에 밀어넣는 순간이 곧 배포다(Vercel 이 GitHub 에 연결돼 있다). 검사를 통과하지
못한 코드가 그대로 사용자에게 갔을 수 있다는 뜻이다.

관행으로는 이미 PR 만 쓰고 있었다(#82~#89 전부 PR). 그러나 **관행은 장치가 아니다** —
급할 때 한 번, 세션이 착각했을 때 한 번이면 뚫린다. 이 저장소는 이미 여러 세션이 한
PC 에서 병렬로 도는 환경이라 "지금 어느 가지에 있는지" 착각이 실제로 사고를 냈다.

## 결정 1 — 잠금은 **GitHub 쪽**이 진짜다

저장소 규칙 `main 보호`(target=branch, enforcement=active)를 만들었다. 규칙 넷:

| 규칙 | 뜻 |
|---|---|
| `pull_request` | PR 을 거쳐야 한다 |
| `required_status_checks` | 검사 `test`·`web` 둘 다 통과해야 한다 |
| `non_fast_forward` | 강제로 역사를 덮어쓰지 못한다 |
| `deletion` | main 가지를 지우지 못한다 |

**말이 아니라 실측으로 확인했다.** 빈 커밋을 만들어 직접 밀어넣어 보고 거부를 받았다:

```
remote: error: GH013: Repository rule violations found for refs/heads/main.
remote: - Changes must be made through a pull request.
remote: - 2 of 2 required status checks are expected.
```

### 승인자는 **0명**으로 둔다 (중요)

`required_approving_review_count: 0`. 승인자를 1명이라도 요구하면, **자기 PR 은 자기가
승인할 수 없다**는 GitHub 규칙 때문에 혼자 일하는 지금 상태에서 **어떤 PR 도 영영
머지되지 않는다.** 잠금이 아니라 자물쇠에 열쇠를 넣고 부순 셈이 된다.

검사(`test`·`web`)가 통과 조건이므로, 승인 0명이어도 "아무 검사 없이 들어가는 길"은 없다.

### 검사에 넣은 것과 **일부러 뺀 것**

실측한 검사 이름은 여섯이었는데, required 로 넣은 것은 둘뿐이다.

| 검사 | required? | 이유 |
|---|---|---|
| `test` (파이썬) | ✅ | 모든 PR 에서 돈다(`pull_request:` 트리거, 경로 필터 없음) |
| `web` (프론트+E2E) | ✅ | 위와 같음 |
| `health` · `digest` | ❌ | **예약(schedule) 전용이라 PR 에서는 아예 안 돈다.** 넣으면 모든 PR 이 영원히 "검사 기다리는 중"으로 멈춘다 |
| `Supabase Preview` | ❌ | 우리 코드와 무관한 이유로 머지가 막힌다 |
| `Vercel` | ❌ | 배포 상태라 코드 정합성 판정이 아니다 |

`integration_id: 15368`(GitHub Actions)을 함께 지정해, 다른 앱이 같은 이름의 검사를
"성공"으로 보고해 통과시키는 길도 닫았다.

#### 함께 정해진 값 하나 — `strict_required_status_checks_policy: false`

> 📌 **2026-08-25 감사 배치에서 추가.** 이 값이 규칙에 들어 있는데 이 문서에 한 줄도
> 없었다. 라이브 실측 = `false`. 판단 기록이 없으니 **의도적으로 끈 것인지 기본값 그대로인지는
> 알 수 없다** — 그래서 "무엇을 뜻하는가"만 남긴다.

켜면(`true`) **"내 가지가 main 최신 상태여야 머지할 수 있다"**가 된다. 남의 PR 이 하나
들어갈 때마다 내 가지를 main 과 다시 맞추고 검사를 다시 통과해야 한다.

| | 지금(`false`) | 켰을 때(`true`) |
|---|---|---|
| 머지 조건 | 검사 `test`·`web` 통과 | 그 + **main 최신 상태** |
| 잡는 것 | 그 가지 안에서 깨지는 것 | **합쳐졌을 때만 깨지는 것**(각자는 초록인데 합치면 빨강) |
| 대가 | 없음 | 남의 PR 이 들어갈 때마다 내 가지를 다시 맞추고 검사를 다시 기다린다 |

지금은 대체로 한 번에 한 가지씩 순차로 작업해서 실익이 작다. **여러 가지를 동시에 열어
두는 방식으로 바뀌면 그때 다시 볼 것.** 켜는 방법:

```bash
gh api -X PUT repos/developer-duno/sangga/rulesets/21308611 --input <수정한-ruleset.json>
```

### 우회 허용자(bypass)는 **비워 둔다**

관리자를 우회 목록에 넣으면 잠금이 사실상 없는 것과 같다. 긴급 상황에는 **규칙을 잠시
끄는 길**이 어차피 있으므로(저장소 소유자 권한) 탈출구가 없어지는 것은 아니다. 다만 그
경우 "껐다"는 행위가 기록으로 남는다 — 조용히 지나가지 않는 편이 낫다.

## 결정 2 — 로컬 훅은 **잠금이 아니라 알람**이다

`.githooks/pre-commit`(main 에서 커밋 금지)·`.githooks/pre-push`(main 으로 밀어넣기 금지)를
저장소에 담고 `core.hooksPath` 로 켠다.

**로컬 훅을 잠금으로 여기면 안 된다.** 끄면 그만이고, 다른 컴퓨터에는 없다. 그런데도
두는 이유는 **시점**이 다르기 때문이다:

```
   [커밋 직전]        [밀어넣기 직전]        [서버]
   pre-commit    →    pre-push        →    GitHub 규칙
   (알람)             (알람)                (진짜 잠금)
```

GitHub 규칙만 있으면 커밋을 다 만든 뒤에야 거부당해 **가지를 새로 파고 커밋을 옮기는
뒷수습**이 남는다. 로컬 훅은 그 뒷수습 자체를 없앤다.

`pre-push` 가 따로 필요한 이유는 `pre-commit` 이 못 잡는 길이 있어서다 — 다른 가지에서
커밋해 놓고 `git push origin HEAD:main` 처럼 **도착지만 바꿔** 밀어넣는 경우다.

빠져나가는 길은 `SANGGA_ALLOW_MAIN=1` 하나로 통일했다.

## 결정 3 — 훅은 `.git/hooks` 가 아니라 `.githooks` 에 담는다

`.git/hooks/` 안의 파일은 **git 이 추적하지 않는다.** 새로 내려받거나 다른 컴퓨터에서
열면 그냥 없고, 없다는 사실조차 알려주지 않는다. 그래서 저장소에 `.githooks/` 로 담고
새 컴퓨터에서는 한 명령으로 켠다:

```bash
python scripts/setup_git_hooks.py
```

이 명령은 **로컬과 GitHub 양쪽을 함께** 보여준다. 한쪽만 보면 "잠긴 줄 알았는데 안
잠긴" 상태를 못 잡기 때문이다.

### "확인 못 함"과 "없음"을 섞지 않는다

`--check` 는 GitHub 쪽을 `gh` 로 확인하는데, `gh` 가 없거나 네트워크가 없는 환경도 있다.
그때 **"확인 못 함"을 "잠금 없음"으로 취급하면 CI 에서 늘 빨간불이 되고, 결국 이 가드가
꺼진다.** 그래서 확인 실패는 실패로 치지 않고, **확인에 성공했는데 잠금이 없는 경우에만**
종료코드 1 을 낸다.

## 결정 4 — 줄바꿈을 못 박는다 (`.gitattributes`)

윈도우 기본 설정(`core.autocrlf=true`)에서 내려받으면 훅의 줄바꿈이 CRLF 로 바뀐다.
그러면 첫 줄이 `#!/bin/sh\r` 이 되어 셸이 훅을 실행하지 못한다.

**그 실패는 막는 쪽으로 기울지 않는다** — 훅이 못 돌면 커밋·밀어넣기가 그냥 통과한다.
즉 알람이 꺼진 줄도 모르고 지나간다. 이 저장소가 이미 같은 성질의 일을 겪었다(예약
감시가 죽은 것을 나흘 뒤에 알았고, 그래서 감시들이 서로를 보게 만들었다).

⇒ `.gitattributes` 에 `.githooks/** text eol=lf` 를 박고, 회귀 가드로 훅 파일에 `\r` 이
섞였는지 테스트가 직접 본다. 실행 비트(100755)도 git 인덱스에서 확인한다 — 리눅스에서
실행 권한이 빠지면 같은 방식으로 조용히 죽기 때문이다.

그 자리에서 빨간불이 된다.

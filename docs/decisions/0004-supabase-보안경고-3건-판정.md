# 결정 0004 — Supabase 보안 경고 3건, 지금은 고치지 않는다

> 작성일 2026-08-10 · 상태: ✅ **판정 완료 (라이브 실측 + 공식문서 + 3중 적대검증)**
> Supabase 대시보드가 CRITICAL 3건을 띄운다. **셋 다 지금 손대지 않는다.**
> 이 문서는 "왜 빨간 불을 켜 둔 채 두는가"를 남긴다 — 안 남기면 다음 세션이 또 고치려 든다.
> 배경: 사장님이 대시보드 경고를 발견해 "3가지 문제도 함께 분석해서 처리해줘" 지시 →
> 조사 3에이전트 + 처방별 적대검증 → 판정.

## 한 줄 결론

**지금 라이브 DB에 실행할 SQL은 0건이다.** 경고 3건은 "지금 데이터가 새고 있다"가 아니라
"이런 구조면 샐 수도 있다"는 **구조 경고**이고, 그중 2건은 **우리가 고민 끝에 고른 설계**라
경고대로 고치면 **화면이 죽거나 개인정보가 더 노출된다.**

## 건별 판정

| # | 경고 (Supabase 린트) | 진짜 위험인가 | 의도된 설계인가 | 조치 |
|---|---|---|---|---|
| 1 | `spatial_ref_sys` RLS 꺼짐 (0013) | **아니오 (지금은)** | 절반 — 설치 위치는 실수, 지금 안 고치는 것은 의도 | **보류** (이미 배포 전 게이트로 확정) |
| 2 | `v_floor_stack` SECURITY DEFINER (0010) | **아니오** | **예** — 마이그레이션에 대안을 기각한 기록 실재 | **보류 + 주석으로 박제** |
| 3 | `v_coverage_stats` SECURITY DEFINER (0010) | **아니오** | **예** — 3건 중 위험 최저(집계 숫자 4개뿐) | **보류 + 주석으로 박제** |

## 왜 고치면 안 되는가 (처방별 반증)

우리 공개 정책은 **"원본 표는 anon에게 401, 집계 뷰만 200"**이다(마이그레이션
`2026-08-08_public_read_policy.sql`). 뷰가 **소유자 권한으로** 원본을 대신 읽기 때문에 성립한다.
경고가 요구하는 `security_invoker = true`는 정확히 그 구조를 뒤집는다.

1. **`alter table spatial_ref_sys enable row level security`** → 소유자가 `supabase_admin`이라
   **ERROR**. ⚠️ 다른 SQL과 함께 붙여넣으면 **앞 문장까지 전부 롤백되고 뒤 문장은 실행되지 않는다.**
2. **`revoke`로 닫기** → WARNING만 내고 무효(2026-08-08 대조 실측: 같은 문장이 우리 표엔 먹히고
   PostGIS 표엔 안 먹혔다).
3. **`security_invoker = on`** → 중간 뷰 `v_building_floor_stack`이 anon 401이라 **층별 스택 화면이
   전면 사망**. 그런데 **pytest·vitest·E2E가 전부 초록인 채로 라이브만 조용히 죽는다**
   (프론트 테스트는 DB를 가짜로 바꾸고, E2E는 통신을 가로채고, 파이썬 테스트는 SQL 글자만 본다).
   화면을 살리려면 원본 표를 열어야 하는데 그러면 **상호명·개인 성명 노출이 오히려 늘어난다.**

⇒ **도구를 따르는 것이 보안을 나쁘게 만드는 경우**다.

## 1번(PostGIS)에 대한 추가 사실

- 이 표는 전 세계 모든 PostGIS 설치본에 동일하게 들어 있는 **좌표계 사전 8,500줄**이고
  **우리 데이터가 한 줄도 없다.** 통째로 읽어가도 얻는 게 0이다.
- 코드 전체에 `ST_Transform`·`ST_DWithin` 호출 **0건**(전수 grep) — 현재 서비스 영향 0.
- ⚠️ **문서 정정**: 노출된 PostGIS 표를 기록상 "3개"로 적었으나 실측은 `spatial_ref_sys` **1개**뿐
  (`geometry_columns`·`geography_columns`는 200이지만 0행).
- 근본 원인은 `schema.sql`이 PostGIS를 `public`에 설치한 것. 새 프로젝트에서 재발을 막으려면
  `create extension postgis with schema extensions;`가 맞다(컨테이너 1회 검증 후 적용 — **미검증**).

## 곁가지로 발견한 진짜 구멍 (별건 — PR #41로 해소)

조사 중 **`revoke ... from public`이 Supabase에서 무효**임이 라이브로 드러났다.
anon 공개키로 도우미 함수 2개를 직접 RPC 호출하니 **HTTP 200**이었다.
원인은 PUBLIC이 실제 롤이 아니라 가상 그룹이고 Supabase가 anon에게 **직접** GRANT하기 때문
(PG 공식 `sql-revoke.html`). **올바른 형태는 `from anon, authenticated`.**
그리고 그것을 막았다고 검증하던 테스트는 **SQL 파일에 글자가 있는지만 보는 거짓 초록**이었다.
→ PR #41에서 마이그레이션·정본·테스트·`알려진한계.md` §4를 함께 고쳤다.
